# Curate game questions

The source of truth is `storage/curated_question_bank/questions.json` in the repository root. This is a new bank: do not import, search, modify, or clear the old SQLite or v3 banks unless the user asks. It is not yet connected to gameplay. Approved question texts are immutable: preserve them exactly as saved. A differently worded question is a new proposal requiring approval and duplicate checks, not an edit to an existing entry.

Each entry also needs a `display_template`: a natural third-person version using `[STORYTELLER]` for the answering player's name, shown to all players. Use `[STORYTELLER]’s` for the storyteller’s possessives rather than `their`, including when the name appears more than once. Possessives referring to someone else may use `their`. Preserve any `[PLAYER]` placeholder for the selected Listener. Adjust verbs and possessives for English grammar (for example, `What do I like most about [PLAYER]?` becomes `What does [STORYTELLER] like most about [PLAYER]?`). Preserve the approved question's meaning, level and other details. The `text` field remains the approved first-person source for semantic checks; do not embed the display template in its place. A missing `display_template` is incomplete, not ready for name-based gameplay.

Use `[STORYTELLER]` instead of `they` when `they` refers to the storyteller alone, even if the placeholder appears more than once; adjust the verb as needed. Preserve pronouns referring to other people or groups. Avoid `themselves` for the storyteller by rephrasing naturally while preserving the approved meaning. If avoiding it would make a template unnatural or change the meaning, flag the wording for the user to decide.

## Propose

1. Read the local bank and `CONTEXT.md` for the game, levels, and theme membership. Inspect questions across the whole bank, including the requested theme, for overlapping situations and likely answers. Use observed gaps and theme distribution as creative guidance, not quotas. If the bank is empty, say so and start broadly.
2. Review available conversation feedback: use approvals and revisions as positive signals, and avoid repeating rejected questions or their unhelpful patterns. Past rejections include contrived or overly specific situations, trivial procedural details, repetitive favorite or activity questions, and close variations of existing questions. A rejection is not a ban on an entire subject; respect later approvals and specific requests. If feedback is unavailable, do not invent it.
3. Consult the question angles in `models.py` and search the web for varied inspiration relevant to the requested theme. Explore distinct aspects and question types, including memories, preferences, dislikes, reactions, future hopes and playful what-ifs when suitable. Use ideas as starting points and write original questions; do not copy source questions. Briefly cite useful sources when presenting the batch.
4. Present 10 numbered English questions by default, or the number the user requests, labeled Shallow or Deep. Default to Shallow unless the user requests otherwise. Make each one a single, natural question with a short, plausible answer; avoid forced, narrow situations. A Deep question should invite meaningful reflection without adding a second question or an automatic 'and why' follow-up. Honor the user's wording preferences, including 'most favorite' when asking for a favorite, and preserve approved wording. Named themes are optional; Random is not a stored theme.
5. Wait for the user's explicit decisions. Preserve edits exactly as proposed; ask about unclear approval rather than interpreting silence as approval. Then present the complete numbered list of questions selected for approval, including any user-provided revisions, exactly as they would be saved. Ask the user to confirm that list and wait for their explicit confirmation before performing duplicate checks or adding anything. Incorporate corrections and repeat the confirmation when the list changes. If the user explicitly chooses to keep an ambiguous match after reviewing it, honor that decision.

## Consolidate approved questions

1. Re-read the bank. For each confirmed question, check exact normalized text and run `.venv/bin/python skills/curate-game-questions/scripts/neighbours.py 'QUESTION'` from the repository root, passing the exact text as one safely quoted argument. It returns up to five nearest bank questions by cosine similarity using OpenAI `text-embedding-3-small` (1536 dimensions). The local `storage/curated_question_bank/embeddings.sqlite3` caches vectors by exact text hash, model and dimensions, including checked candidates; the script synchronizes missing or changed bank entries automatically. It only sends texts without a cached vector to OpenAI. The script loads `OPENAI_API_KEY` through the project's existing environment configuration; never display the key. If embedding or bank access fails, do not add affected questions; report the failure.
2. Compare meaning, not a numerical threshold: a repeat substantially overlaps in situation, perspective, and answer space. A shared subject or wording alone is not enough. Reject clear repeats; ask the user to decide genuinely ambiguous cases. Retrieval can miss repeats, so also review obvious similarities in the batch. Check each subsequent approved question against the updated bank, including earlier additions from this batch.
3. Add only distinct approved texts to the JSON bank, retaining existing entries. Assign a stable UUID, approved text, a reviewed `display_template`, one level (`shallow` or `deep`), zero or more applicable named themes, and UTC acceptance timestamp. Use theme names from the game's current theme definitions, not invented labels. If level is unclear, ask. Save atomically and verify valid JSON and the resulting entries. Run `.venv/bin/python skills/curate-game-questions/scripts/neighbours.py --sync` to link their cached vectors and repair any incomplete bank entries; then run `.venv/bin/python skills/curate-game-questions/scripts/export_csv.py` and verify it matches JSON. JSON is authoritative; do not edit the CSV independently. Report synchronization or export failures and repair before the next check. Do not claim a question was saved until verification succeeds.
4. Report what was added, withheld as a repeat (with its closest match and reason), or left unresolved. Do not publish or integrate the bank into gameplay without a separate request.
